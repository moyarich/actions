# Repository release and publishing

Workspace Tools separates **release drafting**, **release preparation**, and **package publishing**. Its local workflows call implementations in [moyarich/reusable-workflows](https://github.com/moyarich/reusable-workflows); the reusable workflow YAML files do not live in this repository.

| Local workflow | Responsibility |
| --- | --- |
| `.github/workflows/release-draft.yml` | Preview or update a persistent GitHub Release draft |
| `.github/workflows/release.yml` | Resolve and prepare the selected package version and canonical Git release identity |
| `.github/workflows/publish.yml` | Publish the prepared canonical package artifact to selected registries |
| `.github/workflows/reset-release.yml` | Guarded reset of an unpublished release |
| `.github/workflows/restore-release.yml` | Restore release identity from verified historical evidence |
| `.github/workflows/delete-release-tag.yml` | Explicit release/tag deletion |

## First validate the repository state

```sh
npm ci
npm test
npm run build
npm pack --dry-run
```

Commit any required `dist/bin/` updates. Ensure CI's package tests and committed-distribution checks pass at the latest branch head before merging or performing an actual release.

## Release draft

The `release-draft.yml` workflow can run on pushes to `main` or through **Actions → Release Draft**. It discovers publishable packages from npm workspaces, supports the root package, and accepts an explicit package selector for manual dispatch. Its version controls are `version-mode` (`bump`, `package-json`, `exact`), `version-bump`, `exact-version`, and `dry-run`.

On pushes, the package selection is based on the push range, while the draft's accumulated release notes are based on the previous published package release through current `main`. Keep these two boundaries distinct: changing the release-note baseline to a single push would omit prior unreleased changes.

The caller invokes the shared `reusable_discover-packages.yml`, `reusable_select-release-packages.yml`, and `reusable_release-drafter.yml` workflows. It selects the local CLI with `workspace-tools-source: workspace` so draft selection can use this repository's checked-out implementation.

Drafts are persistent reviewer-editable state: new qualifying PR notes are appended without erasing existing manual text or duplicating previously captured entries. Dry runs preview the change without updating a release. Release drafting **does not publish a package**.

## Prepare a package release

Use **Actions → Release** (`.github/workflows/release.yml`). The package selector defaults to `.`. Choose a version mode:

- `bump`: choose a semantic increment such as patch or minor.
- `package-json`: use the version in the selected package manifest.
- `exact`: supply `exact-version`.

Start with `dry-run: true`. The local caller delegates to `reusable_npm-release.yml` with `workspace-tools-source: workspace`. Review the run summary, canonical tag, and changelog section before performing a real release.

The canonical package release tag identifies the source commit and the package version. Registry publication must use the artifact derived from that identity; do not repoint an already-published version at newer source.

## Publish

Use **Actions → Publish** (`.github/workflows/publish.yml`) or the `workspace-publish` CLI. Public npm is the default publishing destination:

| Selection | Destination | Authentication |
| --- | --- | --- |
| `npm` (default) | `https://registry.npmjs.org` | npm publishing credentials / configured approval |
| `github` | `https://npm.pkg.github.com` | GitHub Packages publishing permissions |
| `all` | Both supported registries | Credentials and permissions for each |

`package.json#publishConfig.registry` also defaults to the public npm registry. The `--registry` CLI flag or the Publish workflow's `registry` input explicitly chooses the destination for a given operation. GitHub Packages remains optional for organizations that want an additional GitHub-hosted copy or private/internal distribution.

**Installing the Workspace Tools CLI** from public npm does *not* require a GitHub Packages token. **Publishing a package** is a separate authenticated operation and may require npm staging approval, release tag verification, and registry-specific tokens. The shared npm publish implementation may stage a release pending approval; staging is not proof that the version is already public.

The publish workflow defaults to `dry-run: true` and requires an explicit non-dry-run decision to make registry changes. Keep `verify-git-tag` enabled for normal releases. Use `npm pack --dry-run` for a separate inspection of the package contents.

Local preview:

```sh
npm exec -- workspace-publish . --registry=npm --dry-run
npm exec -- workspace-publish . --registry=github --dry-run
```

`registry` as a **Workspace Tools source** is different from the `npm` or `github` **publication destination**. Do not conflate these two settings.

## Changelog and GitHub Release

Keep `CHANGELOG.md` and the public GitHub Release draft focused on capabilities, new commands/options, observable behavior changes, compatibility improvements and user-facing bug fixes. CI maintenance and internal refactors without a user-visible result belong in development documentation or the pull request, not public release notes.

A staged npm release does not automatically mean the matching GitHub Release is published. Inspect the registry results and GitHub Release state separately; do not assume the two publication stages are identical.

## Reset and historical restore

Reset and Restore are recovery tools, not normal release steps.

- **Reset Release** must not move a canonical tag once that exact package version exists in a supported registry.
- **Restore Release** accepts a typed historical `restore-source`: `commit:<sha>`, `tag:<tag>`, `run:<id>`, `artifact:<id>`, or `github-url:<supported-url>`.
- Restore verifies the candidate package artifact against immutable published copies when publication already exists. A mismatch or unverifiable source stops the operation.
- Immutable GitHub Releases may prevent editing their notes or assets, but this does not change the canonical source identity for a package version.

Prefer a new version for new source after publication rather than attempting to rewrite existing published package bytes.

## Maintaining workflow compatibility

When updating a caller, compare its `with:` keys, allowed values, permission requirements and outputs against the actual `workflow_call` definition in `moyarich/reusable-workflows`. Keep the two repositories in sync when changing source selectors or registry behavior. Use a dry run to validate the change; a successful workflow parse alone does not prove publishing works.

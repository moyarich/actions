# Repository release draft

Workspace Tools keeps its public reusable workflow separate from this repository's own release orchestration.

```text
.github/
├── release-drafter-template.yml        # Release Drafter config template
└── workflows/
    ├── reusable_release-drafter.yml    # public reusable draft implementation
    └── release-drafter.yml             # repository-local caller for moyarich/workspace-tools
```

## Repository-local caller

`.github/workflows/release-drafter.yml` is not part of the public reusable API.

It owns only repository-specific concerns:

- the `Workspace Tools v<version>` release name;
- the default target branch;
- repository-level concurrency; and
- the inputs exposed in the Actions UI.

The repository-local caller delegates draft mechanics to:

```yaml
uses: ./.github/workflows/reusable_release-drafter.yml
```

## Dry run

The repository-local workflow defaults to `dry-run: true`.

A dry run resolves the changelog entry, release name, and draft tag name without creating or modifying a GitHub Release.

## Create or reuse the draft

To create or reuse the repository draft, run `release-drafter.yml` with `dry-run: false`.

The reusable workflow creates or reuses the matching release draft.

It does not create a Git tag and it does not publish the GitHub Release.

If a matching draft already exists, its release-note body is preserved.

## Release Drafter template

`.github/release-drafter-template.yml` owns the draft-note presentation and categorization rules used by the reusable workflow.

It stays outside `.github/workflows/` because files in that directory are reserved for GitHub Actions workflow definitions.

## First-draft source

For a first release draft, the reusable workflow prefers a matching changelog entry.

If the selected changelog file does not exist, or the requested version has no matching changelog section, it falls back to Git history:

- package drafts use commits scoped to that package directory;
- repository drafts use repository-wide commits.

This keeps first-draft generation working for packages that have not started maintaining a changelog yet.

## Package layouts

Package drafting uses the repository's root `package.json#workspaces` declarations rather than assuming every package is a direct child of `packages/`.

Supported package locations include:

```text
repository/
├── package.json
├── packages/
│   ├── foo/package.json
│   └── bar/package.json
├── plugins/
│   └── foo2/package.json
└── tools/
    └── group/
        └── bar2/package.json
```

For example, workspace declarations may include:

```json
{
  "workspaces": ["packages/*", "plugins/*", "tools/*/*"]
}
```

The root package can also participate when `include-root-package` is enabled and it satisfies the package filters.

Package-specific changelog lookup and Git-history fallback always use the discovered package directory, regardless of nesting depth.

## Drafting versus releasing

Release Drafter and npm release are separate workflows with different responsibilities.

```text
reusable_release-drafter.yml  # prepares or updates GitHub Release drafts
reusable_npm-release.yml      # performs the npm package release lifecycle
```

`reusable_npm-release.yml` is not deprecated and is not replaced by Release Drafter. Existing callers should continue using it for release operations.

The Release Drafter workflows prepare release-note state only. The npm release workflow remains responsible for versioning, release commits/tags, package publishing, and final release lifecycle behavior.

## Persistent draft contract

A release draft is persistent state, not generated output.

When no draft exists, the reusable workflow chooses the first available seed in this order:

1. the matching changelog version;
2. Release Drafter pull-request history;
3. scoped Git commit history;
4. a minimal `Initial release.` body.

Once a draft exists, its body is authoritative. Maintainer-authored text is preserved.

Release Drafter runs in dry-run mode to discover newly merged pull requests. Generated pull-request entries include stable hidden markers such as:

```html
<!-- moya-release:pr=123 -->
```

The reconciliation helper appends only entries whose PR marker is not already present. Existing generated entries and manual text are not removed or regenerated.

The draft also records a seed SHA. Release Drafter uses that baseline so pull requests already represented by the initial seed are not replayed on later runs.

For older drafts created before seed metadata existed, the workflow derives a migration baseline from the draft's last update time and then adds the persistent metadata without discarding the existing body.

## Release lifecycle

The canonical package identity and the GitHub Release are related, but registry publication and GitHub Release state are separate concerns:

```text
canonical Git tag
      ↓
source commit
      ↓
canonical package artifact
      ↓
selected registry destinations

matching GitHub Release
      ↓
release notes + optional package assets
      ↓
draft or published state
```

`Reset Release` may move the canonical package tag only while that exact package version is still absent from every supported registry. Once any supported registry accepts the version, Reset refuses to move the source identity.

Registry publishing always derives the canonical package artifact from the commit referenced by the canonical tag. GitHub Release assets are supplemental release artifacts; they do not become the authority for package bytes.

When a matching GitHub Release is mutable, the release-oriented publish workflow can add or replace package assets. When the release is immutable, asset mutation is skipped and a missing registry destination may still be published from the canonical tag/commit.

Publishing to npmjs.org does not itself publish or close a GitHub Release draft. Publishing to GitHub Packages may publish a matching draft; if the GitHub Release is already published, registry publication can continue without changing release state.

`Restore Release` is a separate recovery operation. It accepts one typed `restore-source` value:

```text
commit:<sha>
tag:<tag>
run:<run-id>
artifact:<artifact-id>
github-url:<supported-github-url>
```

The `workspace-release-identity restore-source` CLI resolves that input to one exact full commit SHA before the workflow performs destructive recovery. The workflow then derives the historical package/version/tag identity from that commit.

If the exact package version already exists in one or more supported registries, Restore treats those immutable registry packages as fallback evidence. It rebuilds and packs the candidate commit and compares the normalized package contents with each published copy. The candidate is accepted when it matches **any** published copy. If no published copy matches, or none can be verified, Restore stops before changing the tag or GitHub Release.

This proves artifact equivalence even when the original publishing commit is unknown. A matching candidate commit does not need to be the unique historical source commit; it must reproduce at least one immutable published package exactly.

A `github-url:` may identify a commit, release tag, workflow run, or workflow artifact in the current repository. Cross-repository URLs are rejected.

For repositories with GitHub immutable releases enabled, an immutable release cannot have its notes or assets rewritten. That immutability does not change the canonical tag/commit authority for a package version and does not by itself prevent publication to a registry where that version is still missing.

## Missing-tag recovery

A missing tag during the draft phase is recoverable without pretending that the package is a new release.

If the package version is **not yet published**, Reset Release may recreate the tag at the current target-branch commit:

```text
package.json version
  → canonical release tag
  → current target-branch commit
  → rebuilt and attested .tgz
```

If the package version is already present in a registry, the registry artifact is immutable and Reset must not point the same version at newer source. In that partial-publication state, use Restore Release with a typed historical source such as a workflow run, artifact, tag, commit, or supported GitHub URL. Restore resolves that source to the original full commit SHA, recreates the canonical tag/release identity from that commit, and allows any still-missing registry destination to be published from the restored source. Newer source must use a new package version.

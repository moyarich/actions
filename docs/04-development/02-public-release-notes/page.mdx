# Public changelog and release notes

Treat `CHANGELOG.md` and GitHub Releases as consumer-facing documentation.

A reader should be able to answer:

- Which reusable workflows are available?
- What can each workflow do?
- What new behavior, options, compatibility, or fixes are available to callers?
- Does a change require callers to do anything differently?

## Release-note boundary

Document changes to the reusable workflows that callers can use or observe.

Include:

- new reusable workflows;
- new supported use cases;
- new or changed workflow inputs, outputs, secrets, permissions, or configuration;
- meaningful workflow behavior changes;
- compatibility improvements;
- caller-visible bug fixes; and
- breaking changes or migration steps required by callers.

Do not include changes that do not affect consumers, such as repository maintenance, documentation-only housekeeping, test changes, formatting changes, or other work with no caller-visible effect.

Write entries in terms of what a caller can now do or what behavior changed.

## Initial release

The first release should be a concise capability overview of the reusable workflows.

Group related workflows so consumers can quickly understand the available CI, package, release, publishing, Pages, and repository-tooling capabilities. Avoid narrating the repository's development history.

## Initial release draft

When the first release draft does not yet exist, use the best available public release information in this order:

1. the matching changelog version;
2. release-worthy pull-request history;
3. release-worthy commit history for the release target;
4. a minimal `Initial release.` body.

The matching changelog is preferred because it is the curated description of the released capabilities.

## Existing release drafts

Once a release draft exists, preserve it.

- Do not replace existing maintainer-authored text.
- Do not erase existing release entries.
- Append newly merged, release-worthy changes that are not already represented.
- Do not add the same pull request more than once.
- Do not replay changes that were already represented when the initial draft was created.
- Updating the release version, tag, or name must not discard the existing body.
- Dry-run previews must show the proposed result without changing the draft.

A pull request belongs in the public draft only when it changes something reusable-workflow consumers can use or observe.

## Review checklist

Before publishing a release, verify that:

- every entry describes a reusable workflow capability or caller-visible change;
- the available workflows and their purpose are easy to understand;
- new inputs, outputs, supported use cases, compatibility changes, and meaningful fixes are represented;
- repository-only maintenance is absent;
- existing draft text has been preserved;
- newly added pull-request entries are release-worthy and not duplicated; and
- an initial release reads as a product capability overview rather than a development diary.

# Repository structure

Moya Actions follows the same content ownership boundary used by Console and MoyaForge:

```text
apps/
└── playground/   # presentation app

docs/             # authoritative documentation

examples/         # authoritative copyable callers

src/
└── release-draft-sync/
    ├── core.ts           # reusable release-draft behavior
    ├── action.ts         # GitHub Actions input/output adapter
    └── index.ts          # runtime entry point

tests/
└── release-draft-sync/   # Vitest coverage for core + action adapter

dist/
└── release-draft-sync/   # Vite-built runtime committed for GitHub Actions

release-draft-sync/
└── action.yml            # public standalone action entry point

scripts/                  # repository tooling that is not an action runtime

.github/
└── workflows/            # public reusable workflows plus repository-local callers
```

## Content ownership

`docs/` is the authoritative documentation source.

`examples/` contains authoritative, copyable examples. Examples are organized as first-class content rather than mirroring a consumer repository's `.github/workflows/` path.

`apps/playground/` is presentation only. It may consume documentation and examples from outside its own directory, but it must not duplicate or become the authoritative source for that content.

The playground currently imports `examples/*/workflow.yml` directly as raw source.

## Workflow, action, and source boundaries

`.github/workflows/reusable_*.yml` is the supported cross-repository workflow API. Other workflows in that directory are repository-local callers or maintenance automation.

Standalone JavaScript actions expose reusable executable behavior beneath the workflow layer. Their maintainable TypeScript source lives under `src/<action>/`, Vite writes the committed runtime to `dist/<action>/`, and a top-level `<action>/action.yml` keeps the consumer path concise.

For example:

```text
src/release-draft-sync/
├── core.ts
├── action.ts
└── index.ts
        ↓ vite build
dist/release-draft-sync/
        ↑
release-draft-sync/action.yml
```

The committed `dist/` output lets repository-local workflows use the exact action implementation at the running commit and lets external consumers pin released refs. CI rebuilds action bundles and fails when the committed runtime is stale.

`scripts/*` remains for repository tooling that is not the runtime implementation of a standalone action.

## Why examples are not nested under .github/workflows

The example tree describes examples, not the physical repository layout a consumer must use. A workflow example can still explain that its destination in a consuming repository is `.github/workflows/<name>.yml` without encoding that destination path into the source tree itself.

This keeps the repository structure consistent with Console and MoyaForge while preserving copyable workflow content.

## Dependency boundary

Moya Actions is upstream automation infrastructure. The playground must not require MoyaForge in order to build or run, because MoyaForge may itself consume automation from this repository.


## Action tests

Action source is tested with Vitest under `tests/<action>/`. Keep behavioral reconciliation tests against `core.ts` and GitHub Actions environment/file adapter tests against `action.ts`.

```sh
npm run test:actions
```

The Vite bundle is generated separately with `npm run build:actions`; CI then verifies the committed `dist/` output matches that build.

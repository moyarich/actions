# Repository structure

Moya Actions follows the same content ownership boundary used by Console and MoyaForge:

```text
apps/
└── playground/   # presentation app

docs/             # authoritative documentation

examples/         # authoritative copyable callers

src/
├── release-draft-sync/
│   ├── core.ts
│   ├── action.ts
│   └── index.ts
├── discover-packages/
│   ├── core.ts
│   ├── action.ts
│   └── index.ts
└── issue-dependency-tree/
    ├── core.ts
    ├── github.ts
    ├── action.ts
    ├── cli.ts
    └── index.ts

tests/
├── release-draft-sync/
└── discover-packages/

dist/
├── release-draft-sync/
├── discover-packages/
├── issue-dependency-tree/
└── bin/
    └── issue-dependency-tree.mjs

release-draft-sync/
└── action.yml

discover-packages/
└── action.yml

issue-dependency-tree/
└── action.yml

scripts/                  # repository tooling that is not an action runtime

.github/
└── workflows/            # public reusable workflows plus repository-local callers
```

## Content ownership

`docs/` is the authoritative documentation source.

`examples/` contains authoritative, copyable examples. Examples are organized as first-class content rather than mirroring a consumer repository's `.github/workflows/` path.

`apps/playground/` is presentation only. It may consume documentation and examples from outside its own directory, but it must not duplicate or become the authoritative source for that content.

The playground currently imports `examples/*/workflow.yml` directly as raw source.

## Workflow, action, and source boundaries

`.github/workflows/reusable_*.yml` is the supported cross-repository workflow API. Other workflows in that directory are repository-local callers or maintenance automation.

Standalone JavaScript actions expose reusable executable behavior beneath the workflow layer. Their maintainable TypeScript source lives under `src/<action>/`, Vite writes the committed runtime to `dist/<action>/`, and a top-level `<action>/action.yml` keeps the consumer path concise.

For example:

```text
src/<action>/
├── core.ts
├── action.ts
└── index.ts
        ↓ vite build
dist/<action>/
        ↑
<action>/action.yml
```

The committed `dist/` output lets repository-local workflows use the exact action implementation at the running commit and lets external consumers pin released refs. CI rebuilds action bundles and fails when the committed runtime is stale.

`scripts/*` remains for repository tooling that is not the runtime implementation of a standalone action.

## Why examples are not nested under .github/workflows

The example tree describes examples, not the physical repository layout a consumer must use. A workflow example can still explain that its destination in a consuming repository is `.github/workflows/<name>.yml` without encoding that destination path into the source tree itself.

This keeps the repository structure consistent with Console and MoyaForge while preserving copyable workflow content.

## Dependency boundary

Moya Actions is upstream automation infrastructure. The playground must not require MoyaForge in order to build or run, because MoyaForge may itself consume automation from this repository.

## Action tests

Action source is tested with Vitest under `tests/<action>/`. Keep behavioral reconciliation tests against `core.ts` and GitHub Actions environment/file adapter tests against `action.ts`.

```sh
npm run test:actions
```

The Vite bundle is generated separately with `npm run build:actions`; CI then verifies the committed `dist/` output matches that build.

## JavaScript action convention

Use the same boundary for every standalone JavaScript action:

- `core.ts` contains reusable program logic and does not depend on GitHub Actions environment variables.
- `action.ts` adapts action inputs, outputs, summaries, and files to the core API.
- `index.ts` is a minimal runtime entry point.
- `tests/<action>/` contains Vitest coverage for both core behavior and the action adapter.
- Vite bundles every action entry point into committed `dist/<action>/index.mjs`.
- `<action>/action.yml` exposes the short consumer path `moyarich/actions/<action>@<ref>`.
- Actions that also expose a terminal interface may add `cli.ts`; the CLI delegates to the same core rather than duplicating behavior.
- CLI bundles live under `dist/bin/` and are published through the package `bin` map.
- Interactive terminal integrations such as `fzf` remain optional external tools and do not leak into the non-interactive Action runtime.

The root `dist/` directory is intentionally committed. Nested application/package `dist/` folders remain generated build output and are ignored. Prettier ignores every `dist/` directory because bundled runtimes are generated.

## Reusable workflow review

Reusable workflows remain the orchestration API. A workflow should delegate to a JavaScript action when it contains substantial reusable program logic rather than ordinary command orchestration.

Current action-backed workflows:

| Workflow                                  | JavaScript action       | Reason                                                                                              |
| ----------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------------------- |
| `reusable_release-drafter.yml`            | `release-draft-sync`    | Persistent draft reconciliation, seeding, marker deduplication, and append-only generated state.    |
| `reusable_discover-packages.yml`          | `discover-packages`     | Workspace/direct-child discovery, package filtering, metadata normalization, and matrix generation. |
| `reusable_show-issue-dependency-tree.yml` | `issue-dependency-tree` | Dependency graph normalization, cycle-aware traversal, Markdown rendering, and reusable CLI output. |

The remaining `reusable_*.yml` workflows stay as workflows for now. Their shell/Node fragments primarily coordinate external tools, Git operations, package managers, publishing, Pages, or existing actions rather than exposing an independent reusable JavaScript capability.

# Releasing workspace packages

Use a bump or exact semantic version:

```sh
workspace-release css-expand-collapse=patch
workspace-release css-expand-collapse=minor
workspace-release css-expand-collapse=1.0.0
```

Supported npm version increments are `major`, `minor`, `patch`, `premajor`, `preminor`, `prepatch`, and `prerelease`.

To release the version already stored in the package manifest:

```sh
workspace-release css-expand-collapse --mode=package-json
```

`package-json` does not run `npm version` and does not create a release-only version change. It creates the package-scoped tag, such as `packages/css-expand-collapse@1.0.0`, at the current `HEAD`.

The command requires a clean Git working tree. Bump and exact modes run `npm version` with npm Git tagging disabled, update package release files, create the release commit, and create the package-scoped Git tag.

## Existing tags

Release tags are immutable. A real release fails when the exact package/version tag already exists and never force-moves it.

A dry run reports the conflict without mutating the repository. Its JSON includes the tag state, `canRelease`, and a reason. A tag on another commit therefore produces a warning preview with `canRelease: false` rather than moving the tag.

Multiple package release tags may legitimately point to the same commit when their `package.json` versions are already correct.

## Canonical package release identity

Package releases use:

```text
Version source:          package.json
Git tag:                 <package-directory>@<version>
GitHub Release name:     <package-name> v<version>
Package changelog:       CHANGELOG.md
```

For example:

```text
Package:        @moyarich/workspace-tools
Version:        0.1.0
Git tag:        @moyarich/workspace-tools@0.1.0
Release name:   @moyarich/workspace-tools v0.1.0
```

Use `workspace-release-identity` when another tool or workflow needs the package identity.

The package-specific release job handles versioning, changelog updates, commit creation, and the immutable package tag. GitHub Release creation is a separate release surface from registry publication. A release draft can remain open after npmjs.org publication, and an already-published GitHub Release does not prevent publishing the same canonical package version to a missing registry.

## Separate workflow releases

Reusable workflows are not versioned from `package.json`.

They use:

```text
Version source:          workflow-version.json
Git tag:                 workflows-v<version>
GitHub Release name:     Workspace Tools Workflows v<version>
Workflow changelog:      CHANGELOG_WORKFLOWS.md
Compatible major alias:  workflows-v<major>
```

For example:

```text
workflow-version.json:   0.1.0
Immutable tag:           workflows-v0.1.0
Major alias:             workflows-v0
Release name:            Workspace Tools Workflows v0.1.0
GitHub Release state:    draft
```

The workflow and npm package release lines can advance independently.

## Restore a historical release identity

`Restore Release` uses one typed `restore-source` value and resolves it to the exact historical commit before changing tags or release state.

Supported forms:

```text
commit:<sha>
tag:<tag>
run:<run-id>
artifact:<artifact-id>
github-url:<supported-github-url>
```

Examples:

```text
commit:8b4539e
tag:@moyarich/workspace-tools@0.1.0
run:37624987179
artifact:11484185701
github-url:https://github.com/moyarich/workspace-tools/releases/tag/%40moyarich%2Fworkspace-tools%400.1.0
github-url:https://github.com/moyarich/workspace-tools/actions/runs/37624987179
github-url:https://github.com/moyarich/workspace-tools/actions/runs/37624987179/artifacts/11484185701
```

The resolver records the original source, the resolved source kind, and the full 40-character commit SHA. Resolution happens before destructive recovery steps.

A Restore source is only a way to find the canonical historical commit. Registry publication continues from that canonical tag/commit identity; GitHub Release assets are supplemental and an immutable release does not by itself block publishing a missing registry destination.

### Published-artifact equivalence

When the selected package version is already published, Restore verifies the candidate source before moving release state.

```text
candidate source
  → exact commit
  → build + npm pack
  → normalized package contents
  == any published registry copy
```

If at least one published copy matches, the candidate is artifact-equivalent and may be used for recovery. Mismatches or verification errors from other registries are reported but do not block a verified match. If no published copy matches, Restore fails before changing the canonical tag or GitHub Release.

# Publishing workspace packages

Validate without publishing:

```sh
workspace-publish css-expand-collapse --dry-run
```

A dry run is the publish preflight. It performs the same package validation and packing checks without registry mutation: dependency validation, `typecheck`, `test`, and `build` scripts when present, `npm pack`, registry state checks, and Git release-tag verification by default.

To preview every publishable workspace package:

```sh
workspace-publish --dry-run
workspace-publish --dry-run --json
```

Preview a publish and inspect the suggested distribution tag:

```sh
workspace-publish css-expand-collapse --registry=github --dry-run --json
```

For stable versions the preview suggests `latest`; prerelease versions suggest their prerelease identifier. Suggestions are informational only.

Publish to GitHub Packages by explicitly accepting or choosing a tag:

```sh
workspace-publish css-expand-collapse --registry=github --tag=latest
```

Stage a release for npm:

```sh
workspace-publish css-expand-collapse --registry=npm --tag=latest
```

Before a real publish, Git tag verification is enabled by default. The matching `<package-directory>@<package.json.version>` tag must exist and point to `HEAD`.

To intentionally bypass this condition:

```sh
workspace-publish css-expand-collapse --no-verify-git-tag
```

If the matching tag is valid but the package version already exists in the selected registry, that destination is skipped with reason `already-published`.

Use `--registry=both` for both destinations. `--tag=<tag>` controls the npm distribution tag and `--access=public|restricted` controls access. A real publish is blocked when `--tag` is omitted so `latest` is never moved implicitly.

Before publishing a missing registry version, both dry-run and real publish run each package's `typecheck`, `test`, and `build` scripts when present, then create the exact `npm pack` artifact that would be published. Dry-run stops before registry mutation.

## GitHub Release finalization

The reusable publish workflow resolves the same canonical release identity used by the release drafter and release workflow. Before a real publish it verifies that the matching GitHub draft exists and has the expected release name.

After package publication succeeds, the workflow publishes that existing GitHub Release draft. If npm publication is only staged or the canonical Git tag is absent, the GitHub Release stays in draft state.
